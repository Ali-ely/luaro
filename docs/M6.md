# M6: multi-level undo

## Run and try

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_m6.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_m6.ps1 -Interactive
```

The first command tests and demonstrates undo; the second opens the menu after
testing. Option **10** undoes the most recent successful player edit. The menu
shows the number of undoable edits. The initial eight sample players are setup
and are not part of that history.

Create a default Seer (option 6, role 2, mode 1), duplicate ID 9 (option 8),
modify ID 10 (option 9), and delete ID 10 (option 7). Choose 10 four times:
deletion, modification, duplication, and creation are reversed in that order.
List players between steps. A fifth undo prints `Nothing to undo.` and continues.
Another creation gets ID 11: undo does not recycle assigned IDs.

## Commands and ownership

World records successful management actions on its custom `Stack<Command*>`.
Abstract Command has a virtual destructor and virtual `undo(World&)`. Command.h
and Command.cpp contain four concrete classes:

| Command | Stored state | Undo effect |
| --- | --- | --- |
| CreateCmd | New ID | Remove that player |
| DuplicateCmd | New ID | Remove only the duplicate |
| DeleteCmd | Exact clone and vector position | Insert saved player at that position |
| ModifyCmd | Exact clone and vector position | Replace player with saved state |

Snapshots preserve ID, name, alive/protected flags, concrete role, and all owned
role data. A Witch retains potion usage; a Seer retains inspections. Only normal
duplication assigns a new ID. Historical IDs inside role data remain unchanged.
Restoring a Hunter does not invoke a death reaction.

World owns every Command pointer. DeleteCmd and ModifyCmd own their snapshots
until undo transfers ownership back to World. World pops and deletes commands
after successful undo. Clearing history and World destruction delete unconsumed
commands and snapshots. Stack itself owns its array, not the pointer elements.

Commands cannot be copied. Friendship gives them access to private World
restoration helpers, which do not record commands while undoing an old edit.

Undo of modification replaces the player object with its saved clone. Borrowed
Player pointers to that replaced object become invalid. Retain IDs and look up
the player again, as events already do.

## Editing and gameplay boundary

Only create, delete, duplicate, and modify are undoable. Every successful World
management call records one command, including an edit whose values match the
current values. Unknown IDs and invalid values record nothing. The menu gathers
all input before calling World. `clearUndoHistory()` supports programmatic setup;
the sample village calls it after creating the initial players.

Starting a valid turn discards editing history before actions, even if an
exception interrupts the turn. A refused empty/all-dead turn, zero-turn batch,
or invalid batch request preserves history. Gameplay effects, queued events,
ballots, phase changes, and counters are not undone.

The low-level `processEvents()` helper also clears history when events are
pending, since applying them changes gameplay state. An empty queue preserves
history. Undo and public history clearing are blocked during turns and event
resolution. Post-turn edits can be undone to the post-turn state.

Queued events retain their IDs through undo. Undoing deletion makes the original
ID available to an existing event again. Undoing creation or duplication leaves
safe missing references; events ignore players they can no longer find.

## Failure handling

Edits obtain their command/snapshot and stack space before committing changes.
If vector insertion or name assignment fails, the attempted command and new
object are released, earlier history remains, and no ID is consumed. Deletion
only proceeds after its snapshot is safely recorded.

Undo peeks without popping, attempts restoration, then pops/deletes on success.
If output or insertion throws, the saved command remains available for retry
and retains its snapshot. The ID counter never moves backward. Redo is not part
of the approved milestone plan.

## Validation

Tests cover mixed edits in LIFO order, exact snapshots for all six roles,
first/middle/last positions, empty-world restoration, repeated stack growth,
invalid actions, gameplay boundaries, event references, output failure, and
destruction with unconsumed snapshots. Builds linking World now include Command.cpp.

Verified on 2026-10-24:

- GCC 13.1 with C++17 and `-Wall -Wextra -Wpedantic -Werror`: 157 checks passed.
- Visual Studio AddressSanitizer: 157 checks passed without reported memory errors.
- Visual Studio debug heap: 158 checks passed, including no outstanding allocations.
- M1/M3/M4/M5 regressions: 149 / 724 / 73 / 85 checks passed.
- Scripted menu: mixed edits, repeated and empty undo, history clearing after a
  turn, and EOF during partial input passed.

The unchanged M2 container suite was not repeated. Valgrind was not run on Windows.
