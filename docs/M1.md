# M1: Player hierarchy and deep copying

## What to read first

1. `Player.h` / `Player.cpp`: shared ID, name, alive/protected flags, and the virtual
   interface. `Player` is abstract because it has pure virtual functions.
2. `Teams.h` / `Teams.cpp`: the abstract middle level. Village and wolf roles share
   their team identity; wolves also share their night priority.
3. `Roles.h` / `Roles.cpp`: the six concrete classes and their owned arrays.
4. `examples/m1_demo.cpp`: the original demonstration, including changing a clone
   independently. M3 moved it here so `main.cpp` can demonstrate World turns.
5. `tests/m1_tests.cpp`: executable checks for copying, ownership, and validation.

## What M1 implements

| Role | Owned array | Public operations |
| --- | --- | --- |
| Villager | `SuspicionEntry*` | Set/update a score; read an entry |
| Seer | `InspectionResult*` | Record an exact role; read an inspection |
| Witch | `PotionUse*` | Record potion consumption; check remaining potions |
| Hunter | `int*` | Record/read target IDs of past shots |
| Werewolf | `int*` | Record/read past attack target IDs |
| AlphaWolf | `int*` | Add/read unique pack-member IDs |

Every array starts empty (`nullptr`, count zero) and grows when information is
added. The Witch log can grow to two entries because there are only two potions.
Entries are returned by value, so callers cannot keep a pointer into an array
that might later be reallocated.

These operations record state only. For example, `recordShot()` does not kill
anyone, and `recordPotionUse()` does not enqueue an event. Event effects come in M4.

## Why each role has three special functions

- The copy constructor allocates a new array and copies each entry.
- The assignment operator creates replacement storage, copies the shared base
  state, and then releases the destination's old array. It handles self-assignment.
- The destructor releases the role's array with `delete[]`.

Two small function templates in `Roles.cpp` share the ordinary allocate/copy loops.
They operate only on integers and simple records containing integers, booleans,
or enums. They do not replace the ownership responsibilities of each role.

Allocation happens before old data is discarded. If copying the base name throws,
the temporary replacement array is freed before the exception is rethrown.

## What clone means

`clone()` calls the concrete role's copy constructor. Its result has the same ID,
name, flags, role, and data as the source, but owns separate memory. The caller
owns this new object and must eventually delete it.

For example, if Alice's suspicion score for player 5 is 7, changing her clone's
score to 99 leaves Alice's score at 7. Both IDs remain equal deliberately:
duplication will assign a fresh ID in M5, while undo needs the original ID in M6.
There is no public ID setter in M1.

The base destructor is virtual, so `delete` through `Player*` also runs the
concrete role's destructor. Protected base assignment prevents accidental partial
assignment between different roles through the base interface.

## M1 hooks and later integration

At the M1 checkpoint, `World` was only forward-declared and each `act(World&)`
was an empty hook. M3 now supplies World and phase-dependent action messages.
Builds that include `Roles.cpp` therefore also link `World.cpp`; the commands
below and the M1 build script have been updated. Hunter's death hook remains
empty until M4 can create a ShootEvent.

The simple virtual metadata is ready now: Seer/Witch night priority 0, wolves
priority 1, other village roles priority 2, and AlphaWolf vote weight 2.
The role-name switch is solely a label formatter; it does not dispatch actions.

## Run and inspect

From PowerShell in the project folder:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_m1.ps1
```

The demonstration shows six different concrete roles through base pointers,
followed by the original Villager and its modified independent clone.

To check memory on a Linux g++ installation with AddressSanitizer support:

```sh
g++ -std=c++17 -Wall -Wextra -Wpedantic -g -fsanitize=address -fno-omit-frame-pointer -I. Player.cpp Teams.cpp Roles.cpp World.cpp Event.cpp Command.cpp tests/m1_tests.cpp -o build/m1_asan
ASAN_OPTIONS=detect_leaks=1 ./build/m1_asan
```

The installed Windows MinGW compiler does not provide an AddressSanitizer runtime.
For Windows, use a Visual Studio x64 Native Tools Command Prompt, create
`build\asan` and `build\heap`, and run these commands from the repository root:

```bat
cl /nologo /std:c++17 /EHsc /W4 /WX /MD /Zi /fsanitize=address /I. /Fo:build\asan\ /Fd:build\asan\m1.pdb /Fe:build\m1_asan.exe Player.cpp Teams.cpp Roles.cpp World.cpp Event.cpp Command.cpp tests\m1_tests.cpp
build\m1_asan.exe
cl /nologo /std:c++17 /EHsc /W4 /WX /MDd /D_DEBUG /I. /Fo:build\heap\ /Fe:build\m1_heap.exe Player.cpp Teams.cpp Roles.cpp World.cpp Event.cpp Command.cpp tests\m1_tests.cpp
build\m1_heap.exe
```

AddressSanitizer checks invalid memory access and double deletion. A separate
Windows debug-heap checkpoint checks for outstanding allocations after the tests;
this matters because Windows AddressSanitizer does not provide LeakSanitizer.
The Windows-specific checks are isolated in the test file, not in game classes.

Verified on 2026-10-24:

- GCC 13.1: demo and tests compiled with C++17, `-Wall -Wextra -Wpedantic -Werror`;
  all 149 checks passed, with no compiler warnings.
- Visual Studio AddressSanitizer: all 149 checks passed with no sanitizer errors.
- Visual Studio debug heap: all 150 checks passed, including the check for no
  outstanding allocations after the test suite.
- The demonstration showed the original score staying at 7 while its clone's
  score became 99.

Valgrind was not run on this Windows environment.
