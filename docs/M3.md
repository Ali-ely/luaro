# M3: World ownership and the turn loop

## Files and scope

- `World.h` / `World.cpp`: player ownership, ID generation, lookup/removal, phase
  tracking, and one/multiple-turn execution.
- `Roles.cpp`: six distinct virtual actions, each with Night and Day messages.
- `examples/m3_demo.cpp`: the current World demonstration.
- `tests/m3_tests.cpp`: tests for ownership and turn behavior.
- `build_m3.ps1`: builds and runs the tests and demonstration.

M3's actions are messages only. M4 will add event objects and their effects;
M5-M8 will add the remaining management operations, undo, special actions, and
interactive menu. Winner detection remains in M9. The original M1 demonstration
is preserved in `examples/m1_demo.cpp` and still runs through `build_m1.ps1`.

## One collection with a clear owner

World stores one `std::vector<Player*>`. Each pointer refers to a heap-allocated
concrete role owned by that World. World deletes a player when administratively
removed and deletes every remaining player in its destructor.

Its copy constructor and assignment operator are marked `= delete`, meaning
the compiler rejects copying a World. Copying its owning pointer vector without
cloning the objects would otherwise make two Worlds delete the same players.
Copying individual roles with `clone()` still works exactly as in M1.

`findPlayer()` and `playerAt()` return borrowed pointers. Callers must not delete
them or retain them after removal or World destruction. Lookup by unknown ID
returns `nullptr`; `playerAt()` throws for an out-of-range index. There is also a
const lookup overload for reading a const World.

World uses `std::cout` by default. Tests pass an `std::ostringstream` instead to
inspect action messages. The stream is borrowed and must outlive the World.

## Creating players and assigning IDs

`createPlayer(role, name)` constructs the chosen role with a fresh positive ID,
adds it to the owning vector, and returns its ID. `createPlayer(role)` uses the
role name as a default name. These are the low-level population operations needed
to run M3; user-facing creation, duplication, and modification come later.

The role-selection switch is used only for construction. It does not control
turn behavior. If a constructor fails, the World does not consume an ID. If
adding the new pointer to the vector fails, the new player is deleted.

IDs increase within each World and are never reused after removal. For example,
creating IDs 1, 2, 3, removing 2, and creating again produces ID 4. Different
World instances have separate ID sequences. The integer limit is checked so
ID generation cannot wrap into negative values.

## Night and Day

The world starts at Night. `getPhase()` reports the phase that will execute next.
One completed turn flips the phase. Two turns, Night followed by Day, complete
one round; completed rounds are calculated as completed turns divided by two.

| Method | Meaning |
| --- | --- |
| `runTurn()` | Runs one phase; returns true when it completes |
| `runTurns(n)` | Runs up to n phases; returns how many completed |
| `getCompletedTurns()` | Total completed phases |
| `getCompletedRounds()` | Total completed Night/Day pairs |
| `livingPlayerCount()` | Number of players eligible to act |

Negative requests are rejected; zero turns is a no-op. Empty worlds and worlds
with no living players print a message and do not advance phase or counters.
A multi-turn request stops at that point rather than repeatedly running empty
turns. Counter overflow is rejected before a requested batch starts.

## Virtual action dispatch

At night, World makes three simple passes over the original player vector:

| Virtual `nightOrder()` | Current roles |
| --- | --- |
| 0 | Witch and Seer |
| 1 | Werewolf and AlphaWolf |
| 2 | Villager and Hunter |

For each priority, it calls `act(*this)` on living players whose virtual priority
matches. Players in the same priority group act in their existing list order.
The owning vector is never sorted, preserving positions needed by future undo.
If another priority is introduced later, the scheduler's supported range must
also be updated.

During Day, World walks the vector once and calls each living player's `act()`.
The turn loop has no `dynamic_cast`, `typeid`, role switches, or role-name checks.

Each concrete `act()` checks the current phase and prints its own message:

| Role | Night message describes | Day message describes |
| --- | --- | --- |
| Villager | Observing suspicious activity | Considering suspicion scores |
| Seer | Preparing an inspection | Consulting inspection results |
| Witch | Checking available potions | Preparing a normal vote |
| Hunter | Standing watch and preparing retaliation | Voting while keeping a final shot ready |
| Werewolf | Preparing the pack attack | Planning a vote against the village |
| AlphaWolf | Coordinating the pack | Preparing a double-weight vote |

No votes, damage, inspections, potion consumption, or protection expiration are
applied yet. These belong to M4's event-resolution stage before the phase flips.
The Witch message reads her existing potion log but does not consume a potion.

## Dead versus removed

A dead player stays in the vector, remains inspectable, and is skipped in both
phases. Administrative `removePlayer(id)` deletes the object and erases its
pointer while preserving the relative order of survivors. Removing an unknown
ID returns false. Removal does not call the Hunter's death-reaction hook.

World blocks creation/removal and nested turn execution while a turn is active,
so an action cannot invalidate the collection being traversed. The guard resets
if an action or output operation throws. A failed turn is not counted as complete;
already-written output is not rolled back. M3 has no gameplay event effects to
roll back.

## Run and review

From the repository root in PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_m3.ps1
```

The demonstration creates all six roles in an order different from night priority.
It runs one turn, then three more, and prints four completed turns and two rounds.
It then marks Alice dead to demonstrate skipping, removes the Hunter, and adds a
new player to demonstrate that IDs are not reused.

The M1 and M2 build scripts remain available for regression testing.

For Linux g++ with AddressSanitizer support (create `build/` first):

```sh
g++ -std=c++17 -Wall -Wextra -Wpedantic -g -fsanitize=address -fno-omit-frame-pointer -I. Player.cpp Teams.cpp Roles.cpp World.cpp Event.cpp Command.cpp Capabilities.cpp tests/m3_tests.cpp -o build/m3_asan
ASAN_OPTIONS=detect_leaks=1 ./build/m3_asan
```

For Windows, open a Visual Studio x64 Native Tools Command Prompt, create
`build\m3_asan` and `build\m3_heap`, and run from the repository root:

```bat
cl /nologo /std:c++17 /EHsc /W4 /WX /MD /Zi /fsanitize=address /I. /Fo:build\m3_asan\ /Fd:build\m3_asan\m3.pdb /Fe:build\m3_asan.exe Player.cpp Teams.cpp Roles.cpp World.cpp Event.cpp Command.cpp Capabilities.cpp tests\m3_tests.cpp
build\m3_asan.exe
cl /nologo /std:c++17 /EHsc /W4 /WX /MDd /D_DEBUG /I. /Fo:build\m3_heap\ /Fe:build\m3_heap.exe Player.cpp Teams.cpp Roles.cpp World.cpp Event.cpp Command.cpp Capabilities.cpp tests\m3_tests.cpp
build\m3_heap.exe
```

The separate debug-heap checkpoint checks that player removal and World
destruction leave no outstanding allocations. Tests also cover vector growth,
all six roles in both phases, empty/all-dead worlds, IDs after failed creation,
batch counting, stable scheduling, and recovery after a stream throws.
