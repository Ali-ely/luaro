# M7: Inspector and PotionUser

## Run and try

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_m7.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_m7.ps1 -Interactive
```

The first command tests and demonstrates special actions; the second opens the
menu after testing. The sample village starts at Night, with Witch 1, Seer 2,
Villager 3, and Werewolf 5.

1. Choose 11, acting ID 3, target 5. Villager cannot inspect; the menu continues.
2. Choose 12, acting ID 3, target 5, potion 1. Villager cannot use potions.
3. Choose 11, acting ID 2, target 5. A RevealEvent is queued.
4. Choose 12, acting ID 1, target 1, potion 1. A HealEvent is queued.
5. Choose 12, acting ID 1, target 5, potion 2. A poison KillEvent is queued.
6. View pending events (2), then run one turn (4). Seer learns Werewolf 5's role,
   Witch protects herself, and poison kills 5. The pack's committed attacks
   against Witch 1 are blocked, and protection expires at Night's end.

## Interfaces and checked casts

Capabilities.h declares two small abstract interfaces; their virtual destructors
are defined in Capabilities.cpp:

- Inspector declares `bool inspect(World&, int targetId)`.
- PotionUser declares `bool usePotion(World&, int targetId, bool healing)`.

Seer inherits VillageTeam and Inspector. Witch inherits VillageTeam and PotionUser.
The interfaces hold no data and introduce no additional ownership. The existing
role arrays and deep-copy operations continue to own and copy their data.

World exposes `requestInspection(sourceId, targetId)` and
`requestPotion(sourceId, targetId, healing)` for user-selected actions. Each looks
up a Player pointer, handles an unknown ID, and performs a pointer dynamic_cast
to the requested interface. It checks the result against nullptr before calling
the virtual capability method. An incompatible player prints a message and
returns false. These are the only two dynamic_cast expressions in the project.

Normal Night/Day actions continue through Player::act and virtual event delivery
hooks. They do not use either cast. Multiple inheritance is limited to these
stateless capability interfaces, as required by the approved design.

## Queueing, validation, and undo

The role's capability method queues through the existing manual-event validation.
Both actor and target must exist and be alive. Actions are Night-only; inspection
and poison cannot target self, while healing can. Witch also checks whether the
requested potion remains available. Menu potion input must be 1 (heal) or 2
(poison); invalid input queues nothing.

Capabilities produce RevealEvent, HealEvent, or a poison KillEvent. A successful
request queues an action; it does not immediately reveal, kill, protect, or
consume a potion. Events retain FIFO order, and the effect is applied when the
turn resolves. Explicit inspections can revisit a previously inspected player;
automatic Seer targeting still chooses an uninspected target.

Pending potion requests do not reserve stock. Several requests can queue while
a potion remains, but only the first valid application can consume it. Automatic
Witch healing may also queue; it is ignored if an earlier manual/special heal
already used the potion. A missing/dead target or deleted source causes the event
to be ignored without consumption. Protection also blocks poison.

Special actions are not undo commands. Queueing or rejecting one does not alter
management history. Undo can still remove/restore a referenced player before
the turn begins; ID lookups keep those events safe. Starting a turn or processing
nonempty events clears history under the M6 rules. Special requests are blocked
during a turn or event resolution.

Duplication, delete undo, and modify undo preserve capabilities along with the
concrete role. Copies retain their own potion usage and inspection history.

## Validation

The M7 suite checks all roles against both interfaces, safe incompatible/unknown
IDs, dead actors/targets, self-target rules, Night restrictions, deferred effects,
FIFO protection/poison, repeated requests and single-use inventory, copies/undo,
deleted event references, runtime guards, interface destruction, and mixed turns.
Builds linking Roles.cpp now also link Capabilities.cpp.

Verified on 2026-10-24:

- GCC 13.1, C++17, `-Wall -Wextra -Wpedantic -Werror`: 74 M7 checks passed.
- Visual Studio AddressSanitizer: 74 checks passed without reported memory errors.
- Visual Studio debug heap: 75 checks passed, including no outstanding allocations.
- M1/M3/M4/M5/M6 regression suites: 149 / 724 / 73 / 85 / 157 checks passed.
- Scripted menu checks covered unsupported players, invalid IDs, invalid potion
  choices, queued inspection/heal/poison, spent potions, phase validation, and EOF.

The unchanged M2 containers were not retested. Valgrind was not run on Windows.
