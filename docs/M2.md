# M2: Custom Stack and Queue

## Files and scope

- `Stack.h`: a template stack backed by a dynamic array.
- `Queue.h`: a template queue backed by a circular dynamic array.
- `tests/m2_tests.cpp`: independent container tests.
- `examples/m2_demo.cpp`: a demonstration using readable strings.
- `build_m2.ps1`: builds and runs the tests and demonstration on Windows.

This milestone does not introduce World, events, commands, or the game menu.
The demonstration uses strings such as "Heal player 1" to illustrate ordering;
it does not perform those game actions.

## Stack: newest item first

The stack stores active items in positions `0` through `count - 1`. A push adds
an item at `count`; a pop removes the item at `count - 1`.

| Operation | Result |
| --- | --- |
| `Stack<T> stack;` | Empty stack with capacity 4 |
| `Stack<T> stack(2);` | Empty stack with chosen positive capacity |
| `stack.push(value)` | Copies a value onto the top |
| `stack.peek(output)` | Copies the top into output without removal |
| `stack.pop(output)` | Copies the top into output, then removes it |
| `stack.size()` | Number of active values |
| `stack.isEmpty()` | Whether there are no active values |

`peek` and `pop` return `false` when empty, leaving the output unchanged. A
successful operation returns `true`. A stored null pointer is still a real item;
it is not confused with an empty stack.

## Queue: oldest item first

The queue stores a `first` index as well as its count and capacity. Removing an
item advances `first` instead of shifting every remaining item. New values reuse
the freed positions when the end of the array is reached.

For example, with capacity 3, enqueue 10, 20, 30; remove 10; then enqueue 40:

| Physical array slot | 0 | 1 | 2 |
| --- | --- | --- | --- |
| Stored value | 40 | 20 | 30 |

`first` is 1, so the logical queue order is **20, 30, 40**. Both viewing and copying
follow this logical order. Growth copies those values into the beginning of a
larger array and resets `first` to zero.

| Operation | Result |
| --- | --- |
| `Queue<T> queue;` | Empty queue with capacity 4 |
| `Queue<T> queue(2);` | Empty queue with chosen positive capacity |
| `queue.enqueue(value)` | Copies a value onto the back |
| `queue.peek(output)` | Copies the oldest value without removal |
| `queue.dequeue(output)` | Copies the oldest value, then removes it |
| `queue.at(index)` | Reads the item at a zero-based logical position |
| `queue.size()` | Number of active values |
| `queue.isEmpty()` | Whether there are no active values |

`peek` and `dequeue` return `false` on empty, leaving output unchanged. `at()`
throws `std::out_of_range` for a negative index or an index outside the queue.
To view the entire queue, loop from zero to `size() - 1` and read `at(i)`. No
items are removed, and the next dequeue still returns the original oldest item.

`at()` returns a const reference to the stored value. Use it for immediate viewing;
do not keep that reference across container mutation, assignment, or destruction.
Enqueueing `queue.at(0)` is safe even during growth: the enqueue parameter is
copied before old storage is released.

## Growth and copying

Both containers double their capacity when full, using ordinary loops and
`new[]`/`delete[]`. They reject nonpositive initial capacities and check for
integer overflow before doubling.

Each implements the rule of three:

1. The copy constructor creates independent array storage.
2. Assignment copies into new storage before releasing the old array and handles
   self-assignment.
3. The destructor deletes the array.

If copying into a new array throws, a catch block deletes that temporary array
and rethrows the exception. The original storage is kept. Tests deliberately
trigger this failure during construction, assignment, and growth.

Element types must support default construction, copying, and copy assignment.
This covers integers, strings, and the event/command pointer types needed later.
Unused slots are not read. Removal resets the vacated slot so that a removed
value, such as a large string, does not retain its storage until container exit.

The template implementations are in the headers because a compiler must see the
definitions when creating a `Stack<int>`, `Queue<std::string>`, or another type.
They use basic templates; there are no standard Stack/Queue implementations or
advanced template techniques.

## Ownership when storing pointers

The containers own their arrays, not the objects referenced by pointer values.
Copying a pointer container copies addresses into a separate array; it does not
clone the pointed-to objects.

In M4, event-processing code will dequeue an `Event*`, apply the event, and delete
it. Shutdown will drain and delete remaining events. In M6, undo/history cleanup
will pop and delete `Command*` objects; a command's destructor will release its
saved player clone. Those future owners must not copy an owning history/queue and
then try to delete the same pointed-to objects twice.

This keeps these basic templates reusable for both values and pointers, while
making event and command cleanup explicit at the point that owns those objects.

## Run the demonstration and checks

From the repository folder in PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_m2.ps1
```

Expected demonstration behavior: the stack removes Duplicate, Modify, then
Create. The queue displays Heal, Inspect, Attack without removing anything, then
dequeues those strings in the same order. Empty operations print a clear result.

The tests also exercise 300 successive queue wraparounds, growth while wrapped,
string copies that outlive their source, pointer values, invalid indices, and
deliberate failures in element assignment.

For a Linux g++ installation with AddressSanitizer support (create `build/` first):

```sh
g++ -std=c++17 -Wall -Wextra -Wpedantic -g -fsanitize=address -fno-omit-frame-pointer -I. tests/m2_tests.cpp -o build/m2_asan
ASAN_OPTIONS=detect_leaks=1 ./build/m2_asan
```

For Windows, open a Visual Studio x64 Native Tools Command Prompt, create
`build\m2_asan` and `build\m2_heap`, and run from the repository root:

```bat
cl /nologo /std:c++17 /EHsc /W4 /WX /MD /Zi /fsanitize=address /I. /Fo:build\m2_asan\ /Fd:build\m2_asan\m2.pdb /Fe:build\m2_asan.exe tests\m2_tests.cpp
build\m2_asan.exe
cl /nologo /std:c++17 /EHsc /W4 /WX /MDd /D_DEBUG /I. /Fo:build\m2_heap\ /Fe:build\m2_heap.exe tests\m2_tests.cpp
build\m2_heap.exe
```

The separate debug-heap build measures outstanding allocations after the suite,
including the deliberately failed copies. Windows-specific measurement code is
confined to the tests.

Verified on 2026-10-24:

- GCC 13.1, C++17 with `-Wall -Wextra -Wpedantic -Werror`: 975 checks passed,
  and the standalone demo compiled and ran without warnings.
- Visual Studio AddressSanitizer: all 975 checks passed without sanitizer errors.
- Visual Studio debug heap: all 976 checks passed, including no outstanding
  allocations after the test suite.
- M1 regression: all 149 checks and its demonstration still passed.

Valgrind was not run on this Windows environment.
