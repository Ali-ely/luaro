# M9: victory detection and statistics

## Run and try

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_m9.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_m9.ps1 -Interactive
```

The first command runs tests and the unattended demonstration; the second opens
the console after testing. Option **14** displays statistics at any time. The
menu header also shows the current result. Existing menu numbers are unchanged.

The demonstration uses inspection, healing, and poison, exercises undo, and
runs until a village victory after turn 5. Its report shows 2 completed rounds,
12 accepted ballots, weighted vote total 14, and 6 eliminations. Hunter Dalia's
final shot kills AlphaWolf Farah before the result is decided.

## Outcomes and timing

World tracks one GameResult:

| Result | Condition after a completed turn |
| --- | --- |
| GAME_ONGOING | Living wolves remain and are fewer than living village players |
| VILLAGE_WIN | No living wolves, with at least one village survivor |
| WOLF_WIN | Living wolves equal or outnumber living village players |
| GAME_DRAW | No survivors |

Only living players count. Team membership comes from virtual isWolf(), with no
concrete role checks. The initial result stays In progress during setup. An
empty/all-dead world cannot start a turn; it is not declared an event-chain draw.

Every completed phase first resolves all queued events. Day then tallies ballots
and resolves any Hunter shots created by elimination. Night clears protection.
Only after all of this does World advance the counters/phase and check the
result. Temporary parity during a Hunter chain cannot end the game early.

A winning/drawn turn prints the report automatically. runTurns stops immediately
after that phase; further runTurn requests return false and advance nothing.
Manual events, capability requests, owning enqueue, and low-level vote/kill
helpers reject new gameplay while the result is terminal. Rejected owning enqueue
still deletes its event, honoring its ownership-transfer contract.

## Administrative editing after a result

The console remains available for details, statistics, and editing. Successful
create, delete, duplicate, modify, or undo reopens the simulation by setting the
result to In progress. This includes a valid modification whose values happen
to match. Invalid edits, unknown IDs, empty undo, and clearing history do not
reopen it. The next completed turn determines the new outcome.

Reopening retains counters and history for the same simulation session; it does
not create a new game or replenish potions. Administrative death/revival and
deletion/undo are not gameplay eliminations. They do not alter the recorded past.
Starting another turn still clears editing history under the M6 rules.

## Statistics and attribution

The report includes:

- Result and completed phase count.
- Completed Night/Day rounds, calculated as completed turns divided by two.
  A victory during an initial Night therefore has 1 completed turn and 0 full rounds.
- Cumulative accepted ballots, each counted once per source per Day.
- Cumulative voting weight: ordinary ballot 1, AlphaWolf ballot 2.
- Every actual gameplay elimination, in application order, with source/target
  IDs, saved names, cause, phase, and turn number.

Manual first ballots override automatic duplicates. Repeated, invalid, self,
missing-target, and dead-target ballots add no count. An already committed ballot
from a dead but still present source can count. A valid ballot stays counted even
if its target dies later. Current-Day ballots clear at Night; cumulative totals
remain. A tied/no-vote tally adds no elimination.

Attacks, poison, Hunter shots, and vote eliminations all use World::eliminate.
Protected targets, missing players, repeated attacks on dead players, and stale
event references produce no elimination record. Poison blocked by protection
can consume a potion without recording a death. Village votes use source ID 0
and the collective name Village vote, rather than crediting one voter.

KillRecord stores string copies of the names at the moment of death. Later edits
or deletion cannot erase or rewrite that attribution. Reviving and later killing
the same ID adds another real elimination. killAt returns a separate value and
validates its index. Reports are read-only and can be viewed repeatedly.

The existing low-level processEvents helper does not advance turns, tally votes,
or decide outcomes. Its real effects still enter cumulative statistics; direct
between-turn eliminations use turn number 0 and print Between turns. The console
always uses complete turn execution.

## Exceptions and ownership

Vote totals increment only after ballot insertion succeeds. A kill record is
allocated before changing the target's alive flag. Counts use checked long long
totals; the elimination history is bounded by the int index range. World owns
the record vector and its strings; there are no player pointers in that history.

As in earlier milestones, interrupted turns do not roll back actual effects.
Applied votes/deaths retain their factual statistics, the pending queue is
cleaned, and incomplete turns are not counted or assigned an outcome. An
elimination records the attempted turn number, so a retry can have records with
the same number. Errors printing the final report happen after turn/result
commit and do not undo that completed phase.

## Verification

Tests cover both winning teams, parity and wolf-only cases, a no-survivor draw,
temporary parity during Hunter chains, Day retaliation, stopping batches,
post-game actions, reopening, weighted/duplicate/committed ballots, ties, saved
historical names, invalid history indices, ignored events, interrupted turns,
read-only reports, console access, and repeated complete simulations.

Older test fixtures were adjusted for the new terminal rule. Long scheduling
tests retain enough village players to keep running. Isolated wolf-free Day
tally tests explicitly reopen after Night, rather than disabling victory checks.
Console validation now reserves option 14 for statistics and rejects 15.
